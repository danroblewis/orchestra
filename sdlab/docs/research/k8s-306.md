## Why strategies failed 306

**The rung's new feature, the MIN, was the cause of every none and counts failure at the start.** No
linear row can express `min(0.6 q, 40 ready)`. Every strategy except milp put a linear proxy in its
place:
- 0.432 x queue in the matrix family;
- 22.8 x ready - 4.91 x retries in the lna family;
- 5.51 x retries in censored and its relatives (in none, retries(t+1) = 0.08 x queue(t) exactly).

The error the proxy left in the queue's balance then broke the retries loop (retries -> queue was
missing in 43 of 43 none-short cells) and the traffic gain (wrong in 41).

A probe (review 1, in process, not stored) replaced the MIN by 0.6 x queue and kept the ready stock. With
that change, none-short and counts-short passed for 7 of 7 strategies, one from each found-model group,
and counts-long passed for 4 of 4. So the ready stock does no harm on its own. milp's per-step regime
binaries recovered the MIN exactly (7 of 7 parts). That proved the MIN can be recovered from the data.

**Older causes the MIN exposed:**
- **Counts: the scorer had no standard error.** The noise oracle could not linearise a truth with an
  expression rate, so every 306 part got the bare 10% tolerance. The same retries split had passed 305
  with a measured SE. This is harness, round 2.
- **Counts: the MIN was mis-routed in a few strategies.** In strategies whose base is the pinned
  identify.py or a vendored matrix, the offered MIN series was written as two outside halves. The
  boundary guard then paired them one at a time, with the wrong receiver. This is round 3.
- **Counts: the capped retries drain.** retries empties each step, and the engine caps outflows at the
  level, so the split is biased under counting noise. This was 305's open item. It now decides no cell.
- **Meas: errors in variables.** This was never tested on the counters or the retries loop before:
  304 and 305 have no meas variants.
  - One-step fits on levels with 5% error lose the MIN's kink. The capmin screen does not fire on
    meas-short, and on meas-long the MIN's slope is attenuated to about 0.375 (true 0.6).
  - The fits also misroute inflight's drain as queue -> responses_total, and lose the 0.03 flow into
    errors_total.
  - eiv.py's IV refit stops with "weak instruments", or uses the offered series, which is built from
    noisy levels, as its own instrument.
  - An output-error fit of the true structure passes both meas cells under 3747e29's measured SEs
    (885f8bb). So this is the method's fault, not the data's limit (rule 4b).

A harness bug the MIN exposed: skill@H simulated a found expression rate as 0. milp's exact model read
skill@20 of -41.5%. No status depended on it.

### Refuted: z3exact as impossible

The proposal (k8s-306-r3-six.md): exact search within rounding cannot handle measurement error by
construction (z3.md: "useless on noisy data by construction"). Handling it would need a statistical
estimator, which is a different method. The proposal itself said the reason is the meas variants, not
the MIN.

**Skeptic 1, refuted.** z3exact is never the only passing survivor on any 300-306 cell, nor the best one.
But the rung's mechanism is the MIN, and z3exact passes all four 306 none and counts variants at
3de470a. Measurement error is not new at 306: meas variants have been on the ladder since 300, where
z3exact was kept. z3exact also passes 303 meas-short (c7cade0), so "cannot pass meas by construction" is
contradicted by the store. And 0 of 43 other survivors passed 306 meas when it was proposed, which makes
the failure "not fixed yet", never a reason. If the user wants z3exact out for adding nothing, that would
be a withdrawal, not an impossible elimination.

**Skeptic 2, refuted.** z3exact represents the MIN: 306 none-short is proved identifiable in the
ends/kinds class in 0.4 s. On noisy data z3exact already runs a statistical fallback, `_best_effort`,
which never touches Z3. Making that fallback noise-aware changes only the fallback: an IV or lagged-level
regression, a noise-scaled stop rule, or a copy of oe.py. A scratch try wrapped z3exact with oe.py's
refine (loaded by file path, for the test only; `<scratchpad>/z3oe.py`). On 306 meas-short it was still a
fail at 2/7, but spurious flows fell from 8 to 5, and it took 151 s, over the 120 s timeout. So z3exact
stands where every other survivor stood on meas.

Both refuted, so it is not proposed. Since then, 8 survivors pass 306 meas-short and meas-long with an
added OE stage. That supports skeptic 2: the fix is an added stage.
