# Kubernetes rung 5 (case 304), cause S2: the timeout rate 2x high on counts. Refuted as a bias

**Status:** done (2026-10-20). No code changed. The claimed cause is **wrong**. The found
`queue -> outside` rate (counts-short median 0.1835, counts-long 0.1330, against 0.08) is not a bias.
The seed-304 data themselves point high, and the matrix line's per-row fit adds its own inefficiency on top.
Rung 304 had no failing cells for this cause, and none were cleared.

Everything below was run on commit 974b166 (lna and matrix are unchanged at 7b6d7f4), single-threaded (`OMP_NUM_THREADS=1 OPENBLAS_NUM_THREADS=1
VECLIB_MAXIMUM_THREADS=1 NUMBA_NUM_THREADS=1`). The truth model was simulated with seeds 304.. through
`sdlab.ladder.data.simulate`, the same engine and steps as the cells (the cells use seed 304). The scripts are at the end.

## The estimators over many seeds (seeds.py)

Per seed, each row is fitted by ordinary least squares on the measured levels, with traffic aligned as the
engine applies it (`tr[1:]`, exact on none-short).

| estimator | counts-short (40 seeds) mean / sd / seed 304 | counts-long (30 seeds) mean / sd / seed 304 |
|---|---|---|
| queue row's drain less inflight row's move (what the strategies do) | 0.0831 / 0.0500 / 0.1639 | 0.0785 / 0.0257 / 0.1272 |
| summed row d(queue+inflight+responses+errors) = g x traffic - k x queue | 0.0822 / 0.0387 / 0.1540 | 0.0802 / 0.0157 / 0.1091 |
| the same with the gain fixed at 1 (uses the truth; for reference only) | 0.0799 / 0.0020 / 0.0820 | 0.0798 / 0.0008 / 0.0808 |

The queue-row estimator is unbiased (0.083 and 0.079 against 0.08). Seed 304 is a +1.6 sd draw on
short and +1.9 sd on long. The two variants share the seed, so their errors are correlated. The traffic
gain moves with it (1.139 and 1.080 at seed 304, against 1.019 and 1.001 on average). The fix idea, the
summed row that uses conservation, lowers the sd by 1.3x (short) and 1.6x (long), but at seed 304 it still
gives 0.154 and 0.109. The realization, not the method, accounts for most of the 2x.

## The strategies over seeds (strat_seeds.py)

| strategy (family) | variant, seeds | timeout found | mean | sd | seed 304 |
|---|---|---|---|---|---|
| lna (joint likelihood with counting variance) | short, 20 | 15/20 | 0.0800 | 0.0241 | 0.1333 |
| matrix (= unified at every seed) | short, 20 | **7/20** | 0.1390 | 0.0993 | 0.1879 |
| lna | long, 10 | 9/10 | 0.0710 | 0.0145 | 0.0880 |
| matrix | long, 10 | 10/10 | 0.0863 | 0.0246 | 0.1330 |

The bound SEs (0.0247 short, 0.00943 long) are met by lna on short and are about 1.5x away on long. The
matrix line is about 2x worse. On the stored cells, 22 of the 47 survivors give its 0.1879 (short) and 0.1330 (long).
15 give lna's 0.1333 (short), and 14 give lna's 0.0880 (long). The rest are close variants (0.1767, 0.1351), plus 3 with no timeout on short.
Even at seed 304, lna's 0.133 is 2.1 bound-SE high. That is the data.

## What is really open (not S2's claim): a hidden detection fragility on counts-short

On 13 of 20 counts-short seeds, matrix and unified drop the timeout altogether. They fold it into a lower traffic
gain: seed 305 gives `outside -> queue = 0.8837 x traffic`, with no `queue -> outside`. That is the
structure effect_hats and inflow_effects already return at seed 304, which scores "equivalent". The
smooth daily traffic makes `g x traffic - k x queue` almost collinear with the queue (corr 0.99). Per row,
the timeout is only about 1.6 sd from zero, so the price of a part removes it. The matrix-line strategies pass 304 counts-short
because seed 304 happens to read the timeout high enough to clear the price. On a fresh seed, most of them
would likely be "equivalent". lna finds it on 15/20, because the counting variance (Poisson: variance =
mean) carries information about the rates that a row's mean does not.

Why this was not fixed here:
- No stored cell fails, so a fix could not clear any cell. Any change to the 47 strategies' numbers or structure
  would risk regressions for no measured gain on the ladder.
- The fix that was proposed (the summed or joint row) only narrows the sd by 1.3-1.6x. That would not
  give stable detection on short (2.1 sd), and it would not change seed 304's number much (0.154).
- Doing what lna does (likelihood with the counting variance) in the matrix line would rewrite that
  line's method. That is a question for the coordinator, not a round-1 broad fix.

Suggested next step for the rung (for the coordinator): add a seed-draw case, or a fresh-seed check, for
304 counts-short to measure the detection rate, since rung 305's retries feed off the timeouts. Do not
change the tolerance (it needs the user's approval).

## Scripts

```python
# seeds.py <variant> <n>: per-seed least squares on the queue row and on the summed row
import sys, numpy as np
from sdlab.ladder import cases as casemod, data
c = casemod.load('304-k8s-timeouts-and-errors')
v = sys.argv[1]; N=int(sys.argv[2])
model = casemod.truth_model(c, v)
steps = casemod.variant(c, v)['steps']
def ols(X,y):
    b=np.linalg.lstsq(X,y,rcond=None)[0]; s2=np.sum((y-X@b)**2)/(len(y)-X.shape[1]); return b, np.sqrt(np.diag(s2*np.linalg.inv(X.T@X)))
R=[]
for s in range(304, 304+N):
    d = data.simulate(model, s, steps)
    L=d['levels']; q=np.array(L['queue'],float); i=np.array(L['inflight'],float); r=np.array(L['responses_total'],float); e=np.array(L['errors_total'],float)
    tr=np.array(d['inputs']['traffic'],float)[1:]
    dq=np.diff(q); di=np.diff(i)
    bq,_=ols(np.c_[tr,q[:-1]],dq)
    m=ols(np.c_[q[:-1],i[:-1]],di)[0][0]
    tq=-bq[1]-m
    tot=np.diff(q+i+r+e)
    bs,_=ols(np.c_[tr,q[:-1]],tot)
    # gain fixed 1 on total
    k1=np.sum((tr-tot)*q[:-1])/np.sum(q[:-1]**2)
    R.append((bq[0],tq,bs[0],-bs[1],k1))
R=np.array(R)
for name,col in zip(['gain(qrow)','timeout(qrow-move)','gain(sum)','timeout(sum)','timeout(sum,g=1)'],R.T):
    print('%-20s mean %.4f sd %.4f  seed304 %.4f'%(name,col.mean(),col.std(ddof=1),col[0]))
```

```python
# strat_seeds.py <strategy> <variant> <n>: a strategy's timeout over seeds 304..
import sys, numpy as np
from sdlab.ladder import cases as casemod, data, runner
c = casemod.load('304-k8s-timeouts-and-errors')
strat, v, N = sys.argv[1], sys.argv[2], int(sys.argv[3])
model = casemod.truth_model(c, v); steps = casemod.variant(c, v)['steps']
out=[]
for s in range(304, 304+N):
    d = data.simulate(model, s, steps)
    r = runner.discover(strat, model, d)
    k=None; g=None
    for f in r.get('flows') or []:
        rt=f.get('rate') or {}
        if f.get('from')=='queue' and f.get('to') is None and rt.get('form')=='proportional': k=rt['k']
        if f.get('from') is None and f.get('to')=='queue':
            for t in rt.get('terms') or []:
                if t['stock']=='traffic': g=t['k']
    out.append((s,k,g))
ks=np.array([o[1] if o[1] is not None else np.nan for o in out])
print(strat, v, 'timeout mean %.4f sd %.4f rmse %.4f missing %d seed304 %s' % (np.nanmean(ks), np.nanstd(ks,ddof=1), np.sqrt(np.nanmean((ks-0.08)**2)), np.isnan(ks).sum(), out[0][1]))
print(' ', [None if o[1] is None else round(o[1],3) for o in out])
```
