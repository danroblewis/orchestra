# SD Lab: product and design specification

This document records what the SD Lab prototype settled on, so that the UI and the server can be
rewritten from scratch without losing what was learned. It describes the prototype as it stands
on the `sdlab` branch (last commit `bdb6edf`, plus uncommitted work in progress on discovery, the
runner and the ground-truth examples), checked against the code.

How to read it:

- Sections 1 to 5 describe what exists and what was decided. Where a behaviour came from an
  explicit request by the user, it is marked **(asked for)**. Those are requirements for the
  rewrite, not accidents of the prototype.
- Section 6 is discovery, the part of the project that matters most. It states the contract a
  rewrite must keep, the acceptance criteria, and the known problems.
- Section 7 lists what was not settled, what not to carry over, and open questions.
- Section 8 lists the tests and which of them a rewrite should keep.

Companion documents: [MODEL.md](../MODEL.md) (the model file format, in detail) and
[DISCOVERY.md](DISCOVERY.md) (how the current discovery search works). Where this spec and the
code disagree, the code was checked last; where something is uncertain, it says so.

---

## 1. Purpose and principles

SD Lab is a web app for building, running and, above all, *discovering* system dynamics (SD)
models.

The direction, in order of importance:

1. **Discovery is the product.** Given measured stock levels over time (and, when available,
   measured flow amounts), infer a proper system dynamics model: which flows exist, between which
   stocks, with which equations, and which stocks nobody measures. The UI exists to make this
   usable.
2. **Ground truth first.** Discovery is proven on data generated by known SD models (the `sd-*`
   examples) before it is trusted on real systems. If it cannot recover a model that literally is
   an SD model, simulated with SD Lab's own equations, it is not ready for anything else.
3. **Judge models by what they predict.** "If two models' predictions are nearly identical, then
   both are good." A discovered model whose structure differs from the truth but predicts the
   measured stocks as well as the truth does is a correct answer. Structural agreement is a useful
   diagnostic, not the definition of success.
4. **The UI can be rewritten.** The prototype was mainly useful for finding the UI. Section 4
   records what was found.

The concepts, as the user framed them:

- **Stocks are the measurable things.** Every stock should be measurable, by a count, a query, a
  queue depth, a sensor. A stock is a store of items, not a queue: there is no inherent order
  (a FIFO is one way of taking from it).
- **Flows describe how stocks change**, through an equation (a constant rate, a share of a stock,
  closing a gap to a goal, and so on).
- **Machines do the work, and are applied to flows.** People, programs and AI agents are defined
  separately from the SD model and applied to flows the way a drawing program applies colours.
  A flow takes its machine's colour. Machines are not nodes in the diagram **(asked for)**.
- **The environment** runs flows that happen on their own (arrivals, spoilage). A flow with no
  machine does not run.
- **Discovery infers the model from measurements.** Imagine a flow between every pair of stocks,
  nearly all of them zero, and search for the simplest set that explains the data. Flows to and
  from "outside" that match up hint at a stock nobody measures; fake flows are a sign the chosen
  stocks are wrong.
- **Experiments separate structures.** When the data cannot tell structures apart, change
  something (a machine, a capacity) and run again. Each change to the system starts an **era**,
  and each era keeps a snapshot of the configuration and equations it ran under, so a change can
  be judged against what was predicted for it.

## 2. Concepts and the model format

A model is one JSON file. [MODEL.md](../MODEL.md) has the full format; this section summarises it
and adds what MODEL.md leaves out.

### 2.1 Top level

| Field | Meaning |
|---|---|
| `id`, `name`, `description` | Identity. `id` matches `^[a-z0-9][a-z0-9_-]{0,63}$` and the file name. |
| `time_unit` | One step of a simulation and one tick of a live run ("minute", "day", "5-minute step"). |
| `step_seconds` | Optional. Seconds per step when the unit is not a plain duration (used for axis labels, "real time" speed, and PromQL rates). Not in MODEL.md. |
| `horizon` | How far ahead to project, in time units. Editable from the Run toolbar. |
| `dt` | Simulation step as a fraction of a time unit (default 0.25 in the simulator). |
| `stocks`, `flows`, `machines` | The model. |
| `sensors` | Programs that measure stock levels (and optionally flow amounts and eras) every tick. |
| `history` | A program that prints past levels, one step per line, for "Import history". |
| `era_query` | Optional, PromQL only: a series whose changes start eras. Not in MODEL.md. |

### 2.2 Stocks

| Field | Meaning |
|---|---|
| `id`, `name`, `unit`, `initial`, `x`, `y` | Basics. `x`, `y` is the top-left of the box on the canvas. |
| `target: {value, by}` | A goal: reach `value` by time `by`. Drives the run panel's goal lines and Leverage. |
| `final` | Nothing ever leaves it (done, shipped). Discovery never proposes a flow out of it. |
| `group` | Discovery only proposes flows between stocks of the same group. |
| `inferred: {shape, delay, when, steps}` | Found by discovery, never measured. Its level is what its flows imply (computed in the page). |
| `hide` | Not drawn on the canvas; still in the model and the simulation **(asked for: hide instead of remove)**. |
| `keep` | Simplify never suggests hiding it. |
| `query` | How a sensor measures it (PromQL for the Prometheus sensor). |
| `sensor` | Free text in the stock form ("Measured by"). Vestigial: nothing reads it. Do not carry over. |

In `truth.model.json` files only, a stock may have `"measured": false` (part of the truth, not shown
to discovery).

### 2.3 Flows

| Field | Meaning |
|---|---|
| `from`, `to` | Stock ids, or `null` for outside. At least one is a stock. |
| `rate` | The equation (below). |
| `machine` | A machine id, `"environment"`, or `null` (never runs; drawn dashed grey). |
| `work` | Machine time per unit moved. |
| `ratio` | Units taken from `from` per unit put in `to` (default 1; 2 socks make 1 pair). |
| `outputs`, `split` | Other stocks it may fill; `split` divides the simulated amount between them. |
| `rule` | Live runs: the machine follows the equation as a rule (fires no more often than it says). Without it, the equation only describes what the machine does. |
| `take` | Live runs: what one firing takes, `[{as, from, where?, order?}]`; `where` can relate an input to an earlier one (`{"colour": "a.colour"}`); `order` is `any`, `oldest` or `newest`. Default: one arbitrary item from `from`. |
| `args`, `program` | Program arguments for this flow; `program` is for environment flows in live runs. |
| `effects` | Multipliers from other stocks' levels: `linear` (level / normal, clamped to `[min, max]`, defaults 0 and 1) or `table` (piecewise-linear points). |
| `uses` | Co-flow: each unit moved uses up `per` of another stock; stops when it runs out. |
| `hidden` | Runs in live runs but never reaches the page (stands for the unmodelled real world in teaching examples). |
| `keep` | Simplify never suggests removing or merging it. |
| `query` | Its measured rate per second (PromQL). |
| `found: {when, steps}` | Added from a discovery result. |
| `fitted: {when, before, notes}` | Its equation was replaced by a fit; `before` is the old one. |
| `cloud: {x, y}` | Where the outside end is drawn. |

### 2.4 Equation forms (`rate.form`)

| Form | Rate per time unit | Notes |
|---|---|---|
| `constant` | `value` | |
| `proportional` | `k` × level of `stock` | A drain, a decay, a share. |
| `gap` | (`goal` − level of `stock`) / `time`, never below 0 | Close the gap to a goal. |
| `available` | Everything in the source (÷ ratio) | The machine sets the pace. |
| `linear` | `c` + Σ `k` × level of `stock` over `terms` | What discovery produces when no simpler form fits; also links (a term reading a third stock). |

Every form is clamped at 0. The same forms exist three times, kept in step by hand:
`sim.js` (`desiredRate`), `runner.py` (`desired_rate`) and, via the runner, `sdtruth.py`. A
rewrite should have one definition (see 7.2).

Missing forms that discovery needs (section 6.5): a capacity limit (the smaller of a fitted
maximum and what is in the stock), a rate set by a third stock on a flow between two others, and
fixed delays.

### 2.5 Machines

| Field | Meaning |
|---|---|
| `kind` | `code`, `person` or `agent`. |
| `color` | Its colour on the canvas; new machines take the next unused colour of an 8-colour palette. |
| `capacity` | Time units of work per time unit. |
| `capacity_stock` | Capacity is `capacity` × level of this stock (per worker, per bit). |
| `program`, `args` | The program a live run starts for each firing (named, see 3.1). |
| `prompt`, `timeout` | AI agents (`program: "agents/llm"`): what to do; how long to wait (default 180 s, others 20 s). |
| `description` | Free text. |

A machine shares its capacity across its flows. When the work asked of it exceeds capacity, all
its flows slow down. In the simulator each flow gets an equal share, capped at what it asks for,
with unused share going to the others; the live runner gives the next firing to the flow that has
had least of the machine's time this tick, so the two agree.

### 2.6 Eras and snapshots

An era is a stretch of a run with one configuration of the system. The runner decides when one
starts:

- **The system** is: machines (id, program, args, capacity, capacity stock, prompt), and for each
  flow: ends, outputs, take, machine, work, args, program, ratio, effects, uses and rule; and the
  set of stock ids (`config_key` in `runner.py`).
- **Beliefs and labels** are not the system: equations, names, positions, goals. Changing an
  equation does not start an era; it adds an equations record to the current era.
- An era records `{n, start, label, model, equations: [{t, rates}]}`. The label says what changed
  in plain words ("new machine Shipping desk; Ship now run by Shipping desk").
- **Announced eras**: a sensor reading or a history line may carry `"era": "<label>"` (a deploy, a
  staffing change). That starts an era although the model is unchanged.
- A run recorded before eras existed gets a synthetic era 0, "Before eras were recorded" (page
  only).

Eras are what make experiments readable: each era's chart line is what that era's own equations
predicted from its start, beside what happened **(asked for: snapshots of configurations and
fitted equations, compared change by change)**.

### 2.7 Sensors, history and queries

- A **sensor** is a program run every tick with `{"t", "model", "stocks", "flows"}` on stdin
  (stocks and flows carry their `query`). It prints either `{stock: level}` or
  `{"levels": {...}, "flows"?: {flow: amount this step}, "era"?: label, "time"?: stamp}`.
- A **history** program gets the same input without `t` and prints one
  `{"t", "levels", "flows"?, "era"?, "time"?}` per line, steps counting from 1.
- Measured stocks hold no items; flows cannot take from them.
- Measured flow amounts become the per-stock accounting discovery subtracts (`moved`).

### 2.8 Hidden flows and inferred stocks

Two different things with similar names; a rewrite should name them more clearly:

- A **hidden flow** (`flow.hidden`) is part of the real system the model's author pretends not to
  know. The runner runs it; the server strips it from every response to the page, and saving the
  page's model keeps it. Used by teaching examples (`repair`, `surprises`).
- An **inferred stock** (`stock.inferred`) is a stock discovery proposed from timing and the user
  added. It is in the model, has no measurements, and its level is computed in the page from its
  flows step by step (`fillInferred`).
- A **hidden stock** in a truth model is a stock with `"measured": false`.

## 3. Runs

### 3.1 Live runs of programs

A live run moves real items between stocks by running real programs. The server owns the stocks
and the clock; the page polls.

- **Items.** A stock is a store of items `{_id, _t, ...fields}`. A flow says what it takes
  (`take`); the runner finds a matching set (backtracking over `where` constraints) and takes it,
  so programs never query anything.
- **Programs are named, never given as paths** (`<example>/<name>` resolves to
  `sdlab/examples/<example>/machines/<name>.py`), because anyone who can open the page can edit a
  model. Keep this rule.
- **One firing:** `python <program> <flow args> <machine args>`, stdin
  `{"flow", "flow_name", "inputs": {name: item}, "to": [allowed stocks], "context": {stock: {name, level, sample}}, "prompt"?}`,
  stdout one `{"to": <stock or null>, "item": {...}}` per line. Output to a stock the flow cannot
  fill is an error. A non-zero exit, a timeout or bad output puts the items back.
- **One tick** (one time unit): run sensors; note an era if the configuration changed; on the first
  tick, create each stock's `initial` items (unmeasured models only); fire environment flows as
  often as their equation asks (fractions carry over); let each machine spend its capacity on its
  flows (a `rule` flow fires no more than its equation allows; an effect at or below 0.02 stops a
  flow; overrun is owed to the next tick, unused time is not banked); record levels, firing counts
  per flow (`rates`), machine load, and the exact per-flow accounting of items taken and made
  (`moved`).
- **The log is the run.** Every put, take, tick, era and equations change is appended to
  `$SDLAB_HOME/runs/<model id>/log.jsonl`. A restart replays it. This is the only record.
- **Firings are inspectable.** The last 60 firings keep their argv, stdin, stdout and stderr (each
  truncated to a few KB); the page can open any of them **(asked for: "how do I see the output? Is
  it actually running these programs?")**.
- **Forking helper.** Starting Python costs about 20 ms per firing, most of a trivial program's
  cost. `forkhelper.py` is a long-lived process that forks itself per request (1-2 ms), with the
  same argv, stdin, stdout, stderr, cwd and exit code as a fresh `python <path>`. It falls back to
  plain subprocesses when fork is unavailable or `SDLAB_NO_FORK=1` **(asked for: faster runs)**.
- **AI agents** are machines with program `agents/llm`: an OpenAI-compatible chat call
  (`SDLAB_LLM_URL`, default `http://127.0.0.1:8081/v1`; `SDLAB_LLM_MODEL`) given the items, the
  allowed outputs, the context and the prompt; it writes items like any program.

### 3.2 Measured runs

A model with `sensors` is measured instead of (or as well as) simulated by items:

- **Pacing: a run steps only on new samples.** When every sensor reports a `time` stamp and the
  stamps equal the last step's, no step is taken: a live run cannot go faster than the system it
  measures. The Step button forces a step.
- **No reading, no step.** When no sensor can read anything, no step is recorded (repeating the
  last levels would fill the run with a stretch where nothing happened).
- **Stopping when a source fails.** Three failed reads in a row stop the run, with
  `stopped: {t, reason}` in the snapshot. The page says "The run stopped at day N, because its
  source keeps failing: …. Nothing after that was recorded." **(asked for: a failing source must
  stop the run, not record stale values)**.
- **Import history** runs the `history` program (timeout 30 min), replaces the run with what it
  prints, and records announced eras. A model with a history but no sensors and no programs
  cannot be started (the Start button says to import history instead).

### 3.3 Speed

Speed is model time per real second, labelled in the model's own unit so it cannot be read as a
rate of the model **(asked for: "4 per second" was ambiguous)**: 1 unit every 60 s, every 10 s,
every 2 s, 1 a second, 2, 4, 10, 25 a second, and full speed (`seconds_per_tick: 0`). The option
equal to the unit's real duration is marked "(real time)". At full speed the loop pauses 2 ms per
tick so the page and other runs get a turn; when a measured system had nothing new, 0.5 s.

### 3.4 Ground-truth examples and their unbounded feeds

The `sd-*` examples are the acceptance data for discovery (section 6.3). Each has:

- `sd-<name>.json`: what the page sees. Only the measured stocks, no flows, no machines, a
  `history` program and a `sensors` program. Tests enforce exactly this.
- `sd-<name>/truth.model.json`: an ordinary SD Lab model with every stock (unmeasured ones marked
  `"measured": false`) and every flow, plus `steps`, `long_steps`, `seed`,
  `noise` (`{"counts": true}`: whole-number Poisson amounts; or `{"relative": r}`) and
  `schedule` (`every` N steps, `changes` that replace flow equations at step t; only those marked
  `announce` are reported as eras, the rest happen unannounced as the world's changes do).
- `sd-<name>/truth.json`: the answer key derived from the truth model by `truth.py`
  (`sd_structure`: moves, flows to or from outside, links, hidden stocks). A test checks it is
  current.
- `machines/sim.py`, `live.py`, `history.py`: two-line wrappers around `sdlab/sdtruth.py` and
  `sdlab/livefeed.py`.

Stepping convention (`sdtruth.Truth.run`): one step per time unit, every flow computed from the
levels at the start of the step with SD Lab's equations and effects, outflows of a stock scaled
down together when they would overdraw it, then noise. This is the convention discovery fits.

The live feed (`livefeed.play`) reads step `t` of a recording cached in the temp directory, keyed
by a hash of the example's machine sources. A simulator marked `UNBOUNDED` (all `sd-*`: a longer
run begins exactly like a shorter one) doubles the recording whenever a run goes past it, so the
feed never runs out. The older simulator examples are bounded; past the end the sensor fails and
the run stops cleanly.

The five ground-truth models today:

| Example | Unit | Measured stocks | Unmeasured | Flows | What it exercises |
|---|---|---|---|---|---|
| `sd-pipeline` | day | inbox, working, review, done (final) | none | 5 (constant arrivals; 4 proportional, including rework) | The simplest case: every equation is one discovery has. Unannounced intake changes every 30 days. |
| `sd-saas` | day | ad budget, visitors, trials, paying, churned | lapsed | 11 (a link: ads bring visitors in proportion to budget; a hidden win-back stock) | Links, hidden stocks, announced eras (a price rise). |
| `sd-hospital` | hour | waiting, treatment, ward, discharged | lab | 7 | A hidden stock between two measured ones; day/night arrivals. |
| `sd-kanban` | day | backlog, dev, review, testing, done, bugs | undetected | 9 | Rework loops, a hidden stock feeding a measured one. |
| `sd-supply` | day | warehouse, shop | trucks | 4 (gap forms) | Goal-seeking flows and a shipping delay. |

### 3.5 The older simulator examples

Before the ground-truth examples there were hand-written simulators (Python event or agent
simulations with their own mechanics) exposed through sensors and history: `beergame`,
`bikeshare`, `flu`, `hospital`, `kanban`, `library`, `reservoirs`, `saas`, `shop`, plus the
`factory` (real measurements of Orchestra) and the Prometheus examples (`k8s-fleet`, `k8s-kafka`,
`k8s-kafka-stocks`, backed by `promlab`, a fabricated fleet served over the Prometheus HTTP API).
Each has its own answer key. Their mechanics do not match SD Lab's equation forms, so a failure
on them does not say whether discovery or the example is at fault. See 7.1.

Teaching examples with programs and machines: `bakery` (default), `socks`, `surprises` (hidden
flows), `repair` (hidden backroom), `milling` (effects and co-flows), `roastery` (leverage),
`team` (capacity per staff), `support` (an AI agent machine).

## 4. The UI as it stands

One page, `index.html`, with plain scripts: `sim.js` (simulator, fitting, leverage), `discover.js`
(discovery), `simplify.js` (simplify), `app.js` (everything else, about 2,300 lines). Font IBM
Plex Sans and Mono. Light and dark themes from `prefers-color-scheme`.

### 4.1 Layout

```
+--------------------------------------------------------------------------------------+
| SD Lab | [model picker v] [example] [files][save as] | Edit | Run |        status    |
+------------+---------------------------------------------------------+---------------+
| Machines   | [toolbar: icon buttons, Run mode only]   [find][arrange] | Inspector     |
| [filter]   |                                          [hidden][- fit +]| (context-    |
| palette    |              canvas (SVG): stocks and flows              |  dependent)   |
| + Machine  |                                                         |               |
|            | [hint]                                                  |               |
+------------+------------------ splitter (Run mode) ------------------+---------------+
| Run panel (Run mode only): findings + last program runs | Stocks/Flows tabs, window,  |
|                                                          | scroll, legend, charts grid |
+--------------------------------------------------------------------------------------+
```

- Machines panel 260 px on the left, inspector 300 px on the right, canvas between.
- In Run mode a bottom panel appears under all three. Its height is set by dragging the line
  above it; double-click resets; remembered per browser **(asked for: resizable bottom panel)**.
- Colour tokens: accent (purple) for what happened and selection; `--pred` (teal) for links,
  effects and an era's original prediction; `--fit` (orange) for fits, discovery proposals and
  previews; `--env` grey for the environment; `--unassigned` light grey for flows with no machine;
  good, warn, bad.

### 4.2 Header

- **Model picker**: a custom dropdown, not a native select, so it can show state. Typing filters.
  Arrow keys and Enter choose; Escape closes. Two groups: "My models" and "Examples (open as
  shipped)". A model whose run is going on now has a green background and "▶ running · step N",
  and the picker button itself turns green with a dot when the open model is running
  **(asked for: show which are running, with a background colour)**. The list refreshes every
  few seconds while polling.
- **Example badge**: shown when the open model is an example. Its tooltip says the first change
  saves a copy.
- **Files** (folder icon) opens the files dialog (4.10). **Save as** (disk icon) prompts for a name
  and copies the model and its run; the copy is then what is edited.
- **Edit | Run** tabs. The mode is in the URL hash (`#run`).
- **Status** on the right, monospace: save state ("Unsaved changes", "Saved", "Not saved: …"),
  results ("Found 4 flows in 120 ms"), errors in red.
- The open model is remembered in the URL (`?model=<id>`) and in local storage, and reopened on
  load **(asked for)**. With neither, `bakery`.

### 4.3 Canvas (both modes)

What is drawn:

- **Stocks**: 150 × 64 boxes with the name, the current level and unit, and the goal if any. The
  box fills from the bottom like a tank, to the level as a share of the most it has held so far
  (or its goal, if higher), with the percentage in the corner **(asked for: "full" means the
  maximum seen, for now)**. The present is the live run's latest step, or the projection's start
  when there is no run.
- **Flows**: a straight line with an arrowhead, in the machine's colour, dashed grey when no
  machine. No valve or bow-tie symbols, and no machine nodes: machines are the colour and the
  label of their flows **(asked for: the user disliked standard SD valve notation; machines as
  edge colours, not separate nodes)**. A flow to or from outside ends in a small cloud (three
  circles). Two flows between the same stocks in opposite directions are offset side by side.
  Extra `outputs` branch from the midpoint. Label: the name, then the machine (Edit) or the rate
  now and the machine (Run).
- **Information links**: a dashed grey curve from the stock a flow's equation reads to the
  flow's midpoint; effects dashed teal labelled "effect"; co-flows dotted teal labelled "uses x".
- **Discovery proposals** (orange, dashed, over the model): found flows as curved arrows with
  "amount/unit" (and the ratio); stocks nobody measures as dashed boxes "not measured, holds ~N,
  D units" with arrows from the source (or a dotted "timed by" arrow for an echo) and to the
  target (4.7).
- **Find** highlights matching stocks with an orange border.

Interaction (Edit and Run alike):

| Action | Result |
|---|---|
| Click | Select one thing. |
| Shift-click | Add to the selection **(asked for)**. |
| Ctrl-click | Remove from the selection **(asked for)**. On a Mac the context menu this raises is ignored. |
| Drag on empty canvas | Selection box; shift adds, ctrl removes. |
| Cmd/Ctrl-A | Select every stock and flow. |
| Drag a stock | Moves every selected stock; drag a cloud to move it. Saved. |
| Right-click empty canvas | Menu: "Add a stock here", "Start a flow from outside, here". No add buttons **(asked for: right-click menu instead of + buttons)**. |
| Right-click a stock | "Draw a flow out of this stock", "Hide this stock" / "Show this stock" (or the N selected), "Draw a flow into this stock from outside", "Choose a machine for N selected flows…" when flows are selected, "Delete". |
| Right-click a flow | The machine picker for the selected flows, plus "Delete". |
| Drawing a flow | Pick the source (a stock, or empty space for outside), then the target. The hint line says what to click; Esc cancels. New flows are constant 1 per unit, work 0.1, no machine. |
| M | Machine picker for the selected flows, at the pointer. |
| Delete / Backspace | Delete the selection (flows touching deleted stocks go too; equations that read them become constant 0). |
| Esc | Close menus, cancel drawing, clear the selection. |
| Scroll | Pan. Pinch or ctrl/cmd-scroll zooms around the pointer. |
| Space-drag or middle-drag | Pan. |
| + / − / 0 and the corner buttons | Zoom in, out, fit everything **(asked for: pan and zoom)**. |

Panning and zooming only change the SVG viewBox; the drawing is not rebuilt, so hundreds of
stocks stay smooth.

**Machine picker** (right-click a flow, press M, or "Choose a machine…"): a search box over every
machine, recently applied first, then Environment, No machine, and "New machine '<typed text>'".
A check mark shows the machine all selected flows already use; a dash when mixed. Arrow keys and
Enter **(asked for: many machines, so a searchable picker; multi-select then apply, like a vector
drawing program)**.

**Find stocks** (top right): typing highlights stocks whose name, id or group matches; Enter selects
them and zooms to them; Esc clears.

**Arrange**: lays out the selection (two or more stocks) or everything. Related stocks go in columns
from upstream to downstream (the longest chain leading to a stock decides its column), ordered
within columns by a few sweeps of neighbour averaging so related stocks sit side by side. Related
means a flow between them, a flow whose equation, effect or co-flow reads the other, and the
flows of an open discovery, including its proposed stocks. Unrelated stocks are packed in a grid
by group and name, their clouds placed diagonally. An undo button appears **(asked for: connected
stocks close together; include discovered connections and proposed stocks)**. Arranging an
example saves a copy; it must not change what discovery found (there is a browser check for this,
8.4).

**Show hidden stocks**: an eye button with the count appears when stocks are hidden; it toggles
drawing them.

### 4.4 Machines panel

A palette of machines: filter box (Enter applies the first match), one row per machine with a
swatch, kind chip, number of flows, a busy bar (measured share of the last 20 steps in a run;
otherwise projected), and an edit pencil; then Environment and No machine. With flows selected,
clicking a row applies that machine to them and rows show how many selected flows use them; with
none selected, clicking opens the machine in the inspector. "+ Machine" creates one (and applies
it, if flows are selected).

### 4.5 Inspector

What it shows, in priority order (`inspected()` in `app.js`):

1. A proposed stock picked on the canvas (4.7).
2. The discovery panel, while "keep discovering" is on in Run mode (it stays open **(asked for)**).
3. Leverage, discovery or simplify results, while the selection is the one they were run for.
4. One stock or one flow selected: its form.
5. Several selected: a summary of machines on the selected flows, "Choose a machine…", delete.
6. A machine being edited.
7. A program run (firing) that was clicked.

### 4.6 Run mode

There is one Run view **(asked for)**. An earlier design had separate "Simulate" and "Live"
panels; the user found Simulate redundant ("basically the Live panel with the data paused"). Now:
with no run, the charts show the projection from the starting values; with a run, they show what
happened, and the projection starts from the present.

**The present** is the average of the last few (up to 10) steps of the current era, not the last
single value, so a stock that flips between 0 and 1 does not make the projection jump. The
projection runs the model's equations forward `horizon` time units from there.

a time from the measured levels, then replays the whole stretch with every flow at its first-pass

worked out every 10 steps, not every poll; on more than 8 flows, after drawing.

spending more than about a third of the time fetching and drawing; paused, once a second
**(asked for: more frequent updates)**. Only the parts that changed are redrawn, in place, so
scroll positions and focused inputs are not disturbed **(asked for: "it rerenders constantly and
changes my scroll position")**.

### 4.7 Discovery panel

Opened by 🔍, or kept open and refreshed by 🔄 keep discovering.

- **Scope**: the selected (non-inferred) stocks, or every non-inferred stock. More than 12 stocks
  are split automatically into independent groups (`discoverAll`) **(asked for: discover over the
  whole model, without hand-picking stocks or a 60-stock limit)**.
- **Known flows subtracted**: measured flow amounts, plus what the model's own unmeasured flows'
  equations predict, are subtracted first, so discovery finds what the model is missing. A
  checkbox "Ignore my flows and start from nothing" turns this off.
- **Content**: an introduction (what was explained by what, over how many steps and eras), the
  scope note, the found flows (from → to, amount per step, both ways, the equation per era, and
  "fits about as well" alternatives), a warning when many flows have alternatives (suggesting an
  experiment), stocks nobody measures (where, delay and its plausible range, how much it holds, in
  words), what is not explained (stocks with a steady drift no flow explains), and, when no hidden
  stock was proposed, matched out/in pairs that probably hide one.
- **Proposed stocks are objects on the canvas**: dashed orange boxes placed between the stocks
  they connect (spread apart, never over a stock), draggable, clickable, kept in place across
  refreshes when the same one is found again, and included by Arrange **(asked for)**. Clicking
  one opens its own panel: what it is, holds, delay, shape, flow in, "Add this stock and its two
  flows", "All findings".
- **Approving**: "Add these flows to the model" (when known flows were subtracted) or "Make a new
  model from these flows" (from nothing; the original stays as it is). While keep-discovering is
  on and the run is going, approving is disabled: pause to approve **(asked for: keep predicting;
  the right panel stays open; approve a new flow map when paused)**.
- **What adding does**: found flows join as environment flows with `found` set; a hidden stock
  becomes an `inferred` stock with a flow in (the found rate) and a proportional flow out (1 /
  delay; for a fixed delay this is the nearest form the model has). With keep-discovering on,
  discovery runs again for what the new flows leave unexplained.
- **Keep discovering** reruns when at least 40 steps exist, enough new steps have arrived
  (5, or 1% of the run), and at least max(2 s, 3 × the last run's time) has passed. The panel keeps
  its scroll position across refreshes.

Discovery runs in the page, on the main thread, after a 30 ms timeout. On long runs it freezes the
page (6.5).

## 6. Discovery

### 6.1 The contract

Discovery is a pure function of measurements. It must stay independent of the UI and the server
(today it is a browser script that also runs under Node for tests; it could equally be a Python
module the server calls).

**Inputs**

| Input | Meaning |
|---|---|
| stocks | `[{id, unit, final?, group?}]`: the stocks in scope. |
| run | `{t: [...], levels: {stock: [...]}, rates?: {flow: [...]}}`: one value per step. |
| moved | Optional, per step `{flow: {took: {stock: n}, made: {stock: n}}}`: what is already known (measured flows, and predictions of the model's own unmeasured flows). Subtracted first. |
| eras | Optional `[{start}]`: where the system's configuration changed. |
| start | Optional levels before the first step. Without them, the first step has no change to explain. |
| options | Window, limits on flows and group sizes, switches for links, hidden stocks, pulls. |

**Outputs**

| Output | Meaning |
|---|---|
| flows | `[{from, to, ratio, rate, rates (one per era), perStep, bothWays, nearly (alternatives that fit about as well), driver? (a link), via? (a hidden stock: shape, delay, delayMin, delayMax, holds, atStart, share, echo), screened?, evidence?}]`; `from`/`to` null means outside. Every `rate` is one of the model's equation forms, so a result can be added to a model directly. |
| unexplained | Per stock: `{drift, wobble, persistent}`: a steady drift no flow explains is a sign of a missing flow or stock. |
| hidden | Matched out/in pairs that probably hide a stock (delay, holds), when no hidden-stock flow was accepted. |
| diagnostics | Windows and window width, the search rounds, the score; for whole models, how many stocks were already explained, searched, and in how many groups. |

A rewrite should keep the shape (flows in the model's own forms, per-era coefficients,
alternatives, hidden stocks with delay ranges, the unexplained residue) and should add an explicit
"not enough variation to tell" result instead of falling back to flows to and from outside
(6.5).

### 6.2 The current method, in brief

Details in [DISCOVERY.md](DISCOVERY.md). In one sentence: sparse system identification.

1. Change per stock per step, minus what is known, summed into windows (at least 5 steps, and wide
   enough for at most about 400 windows).
2. Candidate flows between every ordered pair of stocks and to and from outside, pruned by
   `final`, `group`, and unit ratios (2, 3, ½, ⅓ between different units).
3. Each candidate's amount per step is linear in its coefficients:
   `q = c + a × source + b × target` (+ `d × driver` for a link), so any set of flows is one
   weighted least-squares fit. Stocks are weighted by their jitter; one extra row per unit holds
   total change (the conservation evidence). Flows between stocks get coefficients per era; flows
   to or from outside keep one set.
4. Score = BIC + a conservation price for outside flows and unit conversions + a movement price
   (rules out invisible circulation) + extra for hidden-stock flows. Flows must run forwards.
5. Greedy local search from no flows: add a flow, add a chain through a stock, remove, reroute,
   pass through a stock, add a flow through a hidden stock (exp, erlang or pipe delay on a grid of
   about 26 values from 1 to 360 steps, after a correlation pre-screen). Keep the best move while
   it improves the score by more than 2. Tidy equation terms. Report alternatives within 4 points.
6. More than 12 stocks: subtract measured flows, set aside stocks already explained, link stocks
   whose unexplained changes mirror each other (with a bar that rises with the number of pairs),
   union-find into groups of at most 40, search each.
7. Links (an inflow from outside whose rate follows another stock's level) are screened on single
   steps first (`screenLinks`): forward stepwise least squares per target on detrended series, a
   stricter price than BIC, three rules against siblings and shortcuts. Only stocks that turn
   over within a step get screened links. Pulls (a queue falling as a pool gets busier) put the two
   stocks in one group.

`discover.js` is being changed while this is written; treat DISCOVERY.md and the code as the
current state, and this section as the outline.

### 6.3 Acceptance criteria

**The bench** (`tests/bench/`, run with `node --test tests/bench/`, not part of the regular suite):

- `datasets.py <example> [--long]` generates a long run with the example's simulator
  (`measured(seed, steps)`) and caches it outside the repository (`~/.cache/sdlab/bench` or
  `$SDLAB_BENCH_CACHE`), keyed by a hash of the simulator's sources, length, seed and format; for
  `sd-*` examples the hash also covers `truth.model.json`, `sdtruth.py` and `runner.py`. Changing
  a simulator rebuilds its data and removes the old files **(asked for)**.
- `discovery.bench.test.mjs` runs discovery the way the page does (whole model, window 5, the run's
  eras, measured flows subtracted, `discoverAll` above 12 stocks) on:
  - **growing** data: the first 1/32, 1/16, … of the run up to all of it. Does it find the truth,
    and does more data make it better, not worse?
  - **settled** slices: six equal slices of the second half. Once settled, does it keep saying the
    same thing?
- `grade.py` (and `grade.mjs`, for the page's older search) scores a result against the answer key. The headline is **parts of the true model
  recovered in the right form**: each true relationship (move, link, hidden stock, echo) named
  with the right kind, plus each true flow to or from outside. It also reports pairs found, true,
  reversed and wrong; recall and precision; the share of flows that only connect to outside (near
  1 means discovery gave up on structure); a "movement" score per slice (how much the data moved
  beyond step-to-step noise; near 0 means a settled system nothing can be learned from); agreement
  between consecutive slices (Jaccard).
- Quality checks (marked todo until an example passes; graduate an example with
  `SDLAB_BENCH_MEETS`): parts right ≥ 50%; recall and precision ≥ 50%; with all the data, recall no
  more than 10 points below its best and at most 60% of flows only to or from outside; consecutive
  slices agree ≥ 60%. The report is written to `bench-report.md` in the cache folder.

**Ground truth first.** The order of acceptance:

1. `sd-pipeline` (every equation is one discovery has, nothing hidden) recovered completely.
2. The other `sd-*` examples: links (`sd-saas`), hidden stocks (`sd-hospital`, `sd-kanban`,
   `sd-supply`), goal-seeking flows (`sd-supply`), announced and unannounced changes.
3. Only then the older simulators and real data.

**Grading by behaviour (to build).** The user's criterion is that a discovered model is good if
its predictions are nearly identical to the true model's. The bench does not check this yet. It
needs: start the discovered model and the truth model from the same measured state, project both
over a horizon (and across a scheduled change), and compare their trajectories on the measured
stocks against the truth's own noise. The grader should report structural and behavioural scores
side by side, and a structurally different model that predicts as well should pass. Note that the
page's simulator integrates with `dt` (default 0.25) while the truth steps once per time unit
(7.2); the comparison must use one convention.

### 6.4 Where it stands

The most recent bench (October 17, before the current work on discovery): on `sd-pipeline` it
recovers 0 to 2 of 5 parts at any amount of data, with 3 of 4 true pairs found but mostly in the
wrong form; on `sd-saas` 2 to 6 of 10; on the older simulators every example peaks early and
declines as data grows, ending at zero parts for four of them. All quality checks are todo. The
shop's links (DISCOVERY.md section 8) are the one area with good numbers, and that came from
special handling for that example (7.1).

### 6.5 Known problems

| Problem | What happens | Evidence |
|---|---|---|
| **Windows wider than one step bias the fit** | A window's change is the difference of two snapshots, and equation inputs are summed levels; the fitted coefficients come out biased: a true proportional flow of 0.2 comes out as 0.08, and a rework flow comes out negative. | `sd-pipeline`. |
| **The window grows with the run** | The cap of about 400 windows widens windows as the run grows (20,000 steps → 50-step windows); anything faster than a window disappears, and what is left looks like flows to and from outside. "More data, worse answer." | Reservoirs peaks at 80% recall at 6,570 hours and falls to 20% at 26,280 (66-hour windows against 6-hour delays). |
| **Links let wrong models outscore the truth** | A link is an inflow from outside, so it does not conserve; it can fit noise and break conservation, and a non-physical model scores better than the true one. The search finds what the score asks for; the score is wrong. | `sd-pipeline`, `sd-saas`. |
| **One number per flow over long drifting runs** | Only declared eras get their own coefficients; flows to and from outside never do. Years of slow change force one compromise rate. | Kanban (a Done stock growing for five years), SaaS (an ad budget that changes by unannounced campaign). |
| **Missing equation forms** | No capacity limit (min of a maximum and the stock), no rate set by a third stock on a flow between two others, no fixed delay (a 14-day trial is found as an exponential wait), no products (infection ∝ susceptible × sick). | Shop and kanban (capacity), beer game (third stock), SaaS (fixed delay), flu (product). |
| **Settling and lack of excitation** | A system with negative feedback settles; levels stop moving and structures become indistinguishable; the cheapest explanation is a few outside flows or nothing. Discovery should say so rather than guess. | Hospital and flu short runs (movement falls by half to two thirds after start-up). The truth models add unannounced changes so they never settle. |
| **Speed on long runs** | Discovery runs on the page's main thread: 19 s for 5 years of SaaS, 37 s for 3 years of reservoirs, 270 s for the shop's three days. The page freezes. | Bench timings. |
| **Ambiguity of fast pairs and siblings** | At one-second steps, the direction of a link between two fast stocks is a coin toss; stocks sharing a driver also predict a target. | Shop: 6 of 23 false links are reversals, 14 are siblings or ancestors (DISCOVERY.md section 10). |
| **Fast stocks: moves look like links** | At a stock that turns over within a step, the levels cannot tell a move from a link; the screen says link. | Kanban's review column at daily steps. |
| **Inconsistency** | Consecutive slices of a settled run agree on 0 to 60% of relationships. | Every bench example. |

What the evidence suggests for the next discovery (not decided): fit at full resolution (one
step), with a bounded look-back rather than wider windows; make conservation hard rather than
priced (or price links so they cannot beat a conserving explanation); let rates vary over time or
weight periods by how much they moved; add the missing forms; report "not enough variation" and
suggest an experiment; run off the main thread (a worker, or the server).

## 7. Not settled, do not carry over, open questions

### 7.1 Examples and answer keys

- **Answer-key formats differ.** `sd_structure` (the shared format, derived from a truth model),
  the hospital's older format (flows plus named hidden stocks) and the shop's (flows plus
  `driven_inflows`), plus `in_long_runs` additions for some. `grade.py` converts them. A rewrite
  should derive every answer key from a truth model and have one format.
- **The older simulators versus SD-truth examples.** The hand-written simulators (beer game, bike
  share, flu, hospital, kanban, library, reservoirs, SaaS, shop) have mechanics SD Lab's forms
  cannot express, and per-example feed programs. The user's direction is to replace them with
  examples that run SD models, and to bring real data back later. Keep them out of the core
  acceptance set; possibly keep one or two as "realistic" stress tests once SD-truth passes.
- **The shop's special screening.** Link screening on single steps, the "turns over within a step"
  test, pulls and their thresholds were built to make the shop work. They may be right in
  general, but they were tuned on one example. Re-derive them against ground truth before
  carrying them over.
- **Per-example machine programs** (`sim.py`, `live.py`, `history.py` in every example) are
  boilerplate. For SD-truth examples they are two-line wrappers; a rewrite can serve any truth
  model through one generic feed and history.
- **Teaching examples with hidden flows** (`repair`, `surprises`) predate the truth-model idea. A
  truth model with unmeasured stocks does the same job more cleanly.

### 7.2 Engine

- **Three copies of the equations.** `sim.js`, `runner.py` and (through the runner) `sdtruth.py`.
  They are meant to agree and are kept in step by hand. A rewrite should have one engine, or one
  specification with shared test vectors.
- **Two time conventions.** The simulator integrates with `dt` (default 0.25) and fair machine
  sharing; the truth model steps once per time unit from the levels at the start of the step,
  with outflows scaled to what the stock holds. Discovery fits the latter. Projections in the page
  use the former. Decide on one for discovery, projection and grading.
- **`available` form** depends on the step size (`÷ dt`) in the simulator; check it means the same
  in every engine.
- **Flows with no machine do not run** in the simulator, but the truth engine runs every flow.
  Discovered flows are added as environment flows to make them run. A rewrite should make
  "measured system" models not depend on machine assignment.

### 7.3 Server and runtime

- **No authentication**, and the prototype is exposed through a public tunnel. Programs are named
  (not arbitrary commands), which limits the damage, but anyone can edit, delete and start runs.
  Decide before exposing a rewrite.
- **Runs live in server memory** (one `LiveRun` per opened model, never evicted) with a thread
  each. Fine for a prototype; not for many models.
- **Snapshots resend era models** on every full fetch, and the page refetches the whole run when a
  new era appears. Large runs make this slow.
- **`makeFoundModel`** saves to `<id>-found` without checking for an existing model, so a second
  "Make a new model" overwrites the first.
- **`adopt_old_copies`** is a migration for prototype users; drop it.
- **The README is out of date**: it says examples are copied into the models folder on first start
  (they are read-only now).

### 7.4 UI

- **Equations as text.** The user asked not to have to read equations to judge a fit, and the
  chart lines answered that. But the fit list in the findings column, the hover caption and the
  discovery panel still show equations in words, and the user later said "I can't actually see
  what the chosen equation was". Settled: lines first, words as a secondary detail. Not settled:
  how much text, and where.
- **Discovery on the main thread** (6.5). Move it off.
- **`app.js` is one 2,300-line file** with global state and string-built HTML. Two functions
  (`machineStat`) are defined twice. Some CSS rules are dead (`body.fitting`, `body.live-view`).
  None of this should be carried over; the behaviours in section 4 should.
- **Stock fill gauge**: "full" is the most seen so far, explicitly a stand-in until capacity is
  known (from the model, or entered).
- **Find, Arrange and hidden stocks** are fine for dozens of stocks; for hundreds (the fleet), the
  canvas is crowded and Arrange's grid is the only help. Not settled.
- **The stock form's "Measured by" field** does nothing.
- **Hidden flow vs hidden stock vs inferred stock** naming (2.8) confuses; rename.

### 7.5 Prometheus stand-in and real data

`promlab` fabricates a 400-service fleet and serves it over the Prometheus HTTP API; the
`prometheus/promql` sensor and history read any Prometheus (stocks and flows carry PromQL
`query`s; `era_query` marks changes). This is the path to the user's real use (Prometheus metrics
of Kubernetes services, a week or 30 days of history). It worked as plumbing, but discovery on the
fleet found little, and the fleet's simulation had failing requests. Keep the sensor and history
contract (2.7); treat promlab as a test fixture, not a product feature, until discovery passes on
ground truth.

### 7.6 LLM agent machines

The `agents/llm` machine works as plumbing (any OpenAI-compatible endpoint, prompt plus context
plus items). It is the reason machines exist in the design (an AI agent is a general-purpose
machine placed on a flow), but nothing beyond the support-desk example exercises it, and its
variability as a measurement source was discussed but not addressed. Open.

### 7.7 Open questions

- What does "nearly identical predictions" mean numerically (horizon, tolerance relative to noise,
  which stocks)?
- Should discovery see measured flow counters by default in SD-truth examples (`measured()` returns
  every flow's counter; the page subtracts only flows the model names)?
- Should rates be allowed to drift within an era, and how is that shown?
- How should the UI propose experiments when the data cannot separate structures?
- Should the canvas show links (information arrows) for discovered driven flows, rather than an
  inflow from a cloud?
- Unmeasured stocks proposed by discovery become `inferred` stocks with an exponential outflow even
  when the delay was a pipe or erlang shape; the model has no form for those shapes.

### 8.2 What the rewrite should keep

- **The ground-truth example tests** (`test_sd_examples.py`) unchanged in spirit: every truth model
  is a valid model, runs sanely for very long, is prefix-stable, and has a current answer key.
- **The bench**, with the cache outside the repository and keyed by source, the growing and
  settled views, the headline "parts right", and the movement score. Add behavioural grading
  (6.3). As discovery improves, move examples from todo to passing, and make passing examples part
  of the regular suite with a short run.
- **Engine tests**: conservation, non-negativity, ratios, effects, co-flows, capacity per stock,
  fair sharing, with shared vectors run against every engine that implements the equations.
- **Runner tests**: pacing on new samples, no step without a reading, stop after repeated failures,
  restart from the log, eras vs equation changes, hidden flows never leaving the server, named
  programs only, firings keep their I/O.
- **Server tests**: examples read-only, copy-on-edit, copy takes the run, validation, ids.
- **Browser checks** for the interactions that were bugs: Arrange must not change discovery;
  the speed control stays open while polling; scroll position survives polling; a drag selection
  over many stocks does not hang; ctrl-click removes from the selection.

### 8.3 What not to keep

- Per-example discovery thresholds tuned on one simulator (the shop's floors), once ground-truth
  criteria replace them.
- Tests of migration (`adopt_old_copies`).
