## How to work on the models

- **After changing any model:**
  `python3 docs/models/build.py && node docs/models/check.mjs && node docs/models/render.mjs`.
  The user asked for this to be run after every model update.
- **Checks have three kinds:**
  - validity: must pass;
  - requirement: a design target; a gap is reported honestly, never tuned away;
  - info.
- **The SD Lab editor format.** Rate forms: constant, proportional, gap, available, linear (the
  last can read inputs). Effects: table or linear.
  - On a flow with machine time (`work` > 0), an effect changes the machine's **speed**.
  - On a flow without it (environment, or program with `work: 0`), it changes the **rate**.

  So stock-dependent outcomes and routing are parallel no-work flows.
- **Diagrams and charts** are viewed through the `md` viewer (Mermaid 11.4; raw HTML is not
  rendered). Check visual changes with headless Chrome screenshots against port 8799, using a
  `--timeout` (the viewer's live-reload stream keeps the page loading).
- **Every number in the models was hand-written by Claude as an estimate.** Say so; never present
  it as data.

## Decided principles (stated by the user, 2026-10-24)

1. **Orchestra is system-dynamics-first, now and permanently.** It isn't a task manager. Task
   management, agent invocation, review and the gate are *use cases*, implemented by adding
   **machines** to the **factory** (the model).
2. **Machines are attributed to flows.** One machine may serve several flows. A machine doesn't
   define a flow's equation or values.
3. **Flow equations are observed from the actual data** (fitted or discovered). A machine's intended
   effect is a hypothesis, validated against observed equations across eras, not proclaimed.
4. **The real value of the SD Lab work is its strategies for inferring system dynamics equations
   from raw data.** They will be brought into Orchestra (as `orchestra.sd` or a dependency:
   undecided). Don't work inside `sdlab/`.
5. **How to refactor the current task system is proposed, not decided.** The user rejected the
   lazy way (stamping today's whole loop onto flows as one machine). The proposal in
   `proposals/orchestra-kernel.md`:
   - a kernel of twelve primitives (event log, clock, item store, collectors, metrics store, model
     store, inference, machines, dispatcher, executors, adapters, ledger and interventions);
   - the task system rebuilt as about eight small machines;
   - migrated one machine at a time out of `loop.py`.

   Settle its open questions with the user first.
6. **What a machine is** (`proposals/orchestra-kernel.md` §2a, revised 2026-10-25 from the user's
   framing):
   - A machine is outside Orchestra and the model, and may not even respond. Orchestra holds a
     **model of it**: identity, boundary, attributed flows, the collectors that observe it, and
     fitted characteristics.
   - Engaging it is a **request** on the bus, delivered by a **driver**, tracked as a **job** with
     an `unknown` state.
   - Evidence is delivered, claimed or observed. **Only observed evidence counts.**
   - Continuous, ad hoc and scheduled are **engagement modes** for any machine, and AI agents are
     one machine kind.
   - The **bootstrap machine** is Orchestra's own host. It runs the dispatcher, hosts the drivers,
     and is modelled like any machine.
   - **It's the first thing to build after the event bus.**

## Decisions made

- SD-centric design, with task queues and the merge gate as templates.
- Our event and topic space stays separate from company infrastructure; bridges at the boundary.
- Jira and buses share one adapter framework.
- Build the analysis tools as scripts first; move into Orchestra (analyst role, team, tools, store,
  UI) only after two successful runs.

## Next steps (the 2am session, in the Orchestra app)

The user's likely order. Confirm with them first.

1. **An `EventBus` interface** in `orchestra/`:
   - append or publish, subscribe, replay from an offset, per-subject ordering, consumer groups;
   - the current file log as the default implementation;
   - the loop, probes and `wake_on` go only through the interface.
2. **End-to-end acceptance tests against real backends:** Redis Streams and RabbitMQ Streams, maybe
   Kafka (NATS JetStream is the earlier recommendation).
   - One suite runs against every backend.
   - Backends run in containers.
   - Opt-in by environment variable, like `ORCHESTRA_TARGET_URL`.
   - Follow AGENTS.md conventions: `uv`, `pytest`, `ruff`; extend fakes rather than mocking the
     loop.
3. **A first version of the system dynamics core,** following `proposals/orchestra-kernel.md` §4
   (the earlier sketch is §7 of the events proposal):
   - model types and store (stocks, flows, machines, attributions, eras);
   - Orchestra's own factory declared as a model, with no behaviour change;
   - an observer from the event log to flow counts and levels;
   - a first fitter (simplest strategies from SD Lab);
   - validation of machine intent;
   - only then, the loop driven by the model.
4. **Any change to AGENTS.md invariants** (rule 5 state location; rule 2 leases for remote agents;
   rule 1 restated for a model-first loop) must be stated in the commit, per AGENTS.md.

The analysis tools in `analysis-plan.md` (loop finder and others) are still wanted, but come after
the system dynamics core exists in Orchestra.
